# Методы и форматы квантования для локального инференса

**Дата среза:** 24 ноября 2026 года.

**Статус:** методический обзор M1. Ниже приведены кандидаты, а не утверждённый протокол эксперимента.

## Термины, которые нельзя смешивать

| Термин | Что он означает | Пример |
| --- | --- | --- |
| **Формат контейнера** | Структура файла с тензорами и метаданными | GGUF, Safetensors |
| **Алгоритм квантования** | Преобразование весов/активаций/кэша и подбор параметров | GPTQ, AWQ, SmoothQuant, KIVI |
| **Обозначение точности** | Название схемы/типа тензора, часто краткое | Q4_K_M, Q8_0, GPTQ-INT4, W8A8 |
| **Эффективный BPW** | Среднее число фактических бит на параметр вместе со scale/zero-point и смешанными тензорами | Зависит от схемы и модели; не равно номинальной цифре в имени |
| **Квантование весов** | Сжатие постоянных параметров модели | Q4_K_M, AWQ INT4 |
| **Квантование активаций** | Снижение точности промежуточных значений | W8A8, W4A4 |
| **Квантование KV-cache** | Сжатие хранимых ключей/значений внимания во время генерации | KIVI 2-bit; типы cache в runtime |

GGUF — формат хранения, а не единый алгоритм или фиксированная битность. Официальная документация llama.cpp требует GGUF для инференса и описывает конвертацию и квантование отдельно. Краткая метка Q4 не сообщает эффективный BPW, качество калибровки, точность отдельных тензоров, формат KV-кэша или использовавшийся runtime.

## Методы из литературы

| Метод | Что квантуется | Основная идея | Совместимость для сравнения |
| --- | --- | --- | --- |
| GPTQ | Обычно веса, низкая битность | Однопроходная оптимизация по приближённой матрице второго порядка | Для метода нужен backend с поддержкой GPTQ. Сравнение с GGUF требует отдельно выровнять источник, группировку, калибровку и runtime. |
| AWQ | Обычно веса, низкая битность | Activation-aware защита значимых каналов эквивалентным масштабированием | Сопоставим только в отдельном методологическом сравнении; ядра и форматы отличаются от GGUF схем llama.cpp. |
| SmoothQuant | Веса + активации, обычно W8A8 | Перенос outlier-сложности активаций в веса | Нельзя считать прямым контролем против weight-only Q4 GGUF: и точность весов, и активации, и hardware kernel иные. |
| OmniQuant | Веса и/или активации | Обучаемое clipping и эквивалентные преобразования | Нужны отдельная калибровка и реализация; не включать в общий GGUF-когорт без проверки конверсии и kernel. |
| QuIP# / AQLM | Веса, включая экстремально низкие BPW | Векторные/аддитивные кодовые книги и иные структуры квантования | Научно значимы при отдельном сравнении алгоритмов; файлы/ядра/режимы исполнения отличаются. |
| QuaRot / SpinQuant | Веса, активации; в работах также KV-cache | Ротации для уменьшения outlier-чувствительности; SpinQuant обучает параметры ротации | Это end-to-end W/A/KV подходы, не замена одного уровня ggml quant. |
| KIVI / KVQuant | KV-cache | Асимметричная/неравномерная квантовка ключей и значений | Сравнивать только при фиксированных весах и одинаковом prompt/cache/backend. Наличие метода в GPU serving не гарантирует реализацию в Metal. |

## GGUF и схемы llama.cpp

Подходящие для предварительного изучения схемы:

- **Q4_K_M** — смешанная K-block схема с весовым уровнем около 4 бит; фактическое среднее больше номинального и зависит от специальных тензоров/схемы.
- **Q5_K_M**, **Q6_K** — промежуточные уровни для исследования качества/объёма.
- **Q8_0** — контроль меньшего сжатия и более высокого качества; фактическое хранение включает служебные данные и потому не равно ровно 8 бит/вес.
- **Q3_K_M**, **IQ4_XS** — опциональные низкоразрядные/importance варианты, если поддерживаются конкретной архитектурой и точной версией llama.cpp. Их следует маркировать как отдельные схемы, не интерпретировать как линейный уровень битности.

Для каждого артефакта M2 должен записать точное имя типа, версию и commit llama.cpp, исходную ревизию Safetensors, параметры конвертации, использование importance matrix, итоговый размер файла и BPW, рассчитанный по числу параметров и размеру весовых файлов с чётко описанным правилом. Один только суффикс файла недостаточен. Актуальные детали следует перепроверить в [документации quantize llama.cpp](https://github.com/ggml-org/llama.cpp/blob/master/tools/quantize/README.md) и [списке форматов/моделей](https://github.com/ggml-org/llama.cpp/blob/master/docs/models.md).

## Какие сравнения будут корректными

### Общий первичный контур

Для первичного контроля качества методологически проще использовать одну среду: один и тот же точный исходный checkpoint модели, преобразованный в GGUF один раз, затем полученные из него F16/BF16 и квантованные варианты, запуск одной зафиксированной версией llama.cpp/Metal. Так можно изучить разные GGUF уровни при менее меняющемся software stack. Но это будет сравнение **конфигураций llama.cpp/GGUF**, а не доказательство превосходства GPTQ над AWQ или наоборот.

### Сравнение разных алгоритмов

Сравнение GPTQ, AWQ, GGUF и других методов требует как минимум общего исходного checkpoint, одинаковой калибровочной выборки/правила, максимально близкого effective BPW, одинаковых задач и генерации, совместимых backend и измерительного профиля. Если runtime или ядра различаются, результат следует трактовать как сравнение пакетов «алгоритм + формат + реализация + backend», не как чистый эффект алгоритма.

### Отдельное изучение KV-cache

Возможный отдельный этап: зафиксировать модель и весовую схему, сравнить одинаковый контекст при двух-трёх доступных типах cache. Официально доступные в конкретной версии llama.cpp типы cache для K/V следует проверить по документации и на целевой архитектуре. Если применяется KIVI/KVQuant или специализированный backend, это уже новый контур, который нельзя незаметно объединять с GGUF-весовым сравнением. Веса и cache менять одновременно в одном первичном сравнении не рекомендуется.

## Предварительный набор конфигураций

Это **кандидатный диапазон**, не окончательный протокол M2:

1. Для одной выбранной instruct-модели: высокоточный GGUF F16/BF16, если он практически помещается; Q8_0; Q6_K; Q5_K_M; Q4_K_M.
2. Для проверки нижней границы при наличии времени и поддержки: Q3_K_M либо IQ4_XS как отдельная exploratory схема.
3. Для сравнения размеров: несколько параметрических размеров только одной семьи и одного типа постобучения; не смешивать Base, Instruct, Thinking/Reasoning и multimodal в одну линию качества.
4. На первом проходе держать precision KV-cache фиксированной (например, F16), чтобы оценить весовое квантование без дополнительного фактора. Если лимит памяти этого не позволяет, фиксировать причину и отдельно проектировать cache-этап.

## Проект M2: общий путь конвертации

Для основной серии предусмотрен единый runtime `llama.cpp` и GGUF: официальный Qwen3 BF16 checkpoint → общий F16 GGUF intermediate → F16 baseline и Q8_0/Q6_K/Q5_K_M/Q4_K_M derivatives. Так сравниваются GGUF конфигурации от одного source checkpoint. В M2 `imatrix` выключена, чтобы не добавлять calibration-data фактор. Перед реализацией проверить, что pinned converter/quantizer принимает F16 input и выдает нужные tensor types для каждого checkpoint; это ожидает M3 preflight.

| Когорта | Строки M2 |
| --- | --- |
| Qwen3-1.7B | F16, Q8_0, Q6_K, Q5_K_M, Q4_K_M |
| Qwen3-4B | F16, Q8_0, Q6_K, Q5_K_M, Q4_K_M |
| Qwen3-8B | Q6_K и Q4_K_M; Q8_0/Q5_K_M условны по safety pilot; F16 не допускается в целевую 16 GB матрицу |
| Qwen3.5-4B validation | F16 и Q4_K_M; Q6_K для context series, если безопасный pilot проходит; остальные — условны |

Для каждого полученного GGUF сохраняются полный source SHA-40, конвертер/quantizer commit/build, параметры, source/intermediate/artifact SHA-256, размер файла, количество параметров и effective BPW. `Q4_K_M` и другие имена схем — mixed tensor types; фактический BPW следует вычислить по артефакту/числу параметров, а не приравнивать к цифре `4`.

Основная серия держит KV-cache F16, `n_batch=512`, `n_ubatch=128` и один sequence slot. Тип recurrent/state buffers Qwen3.5 фиксируется по runtime log, его архитектурная память не включается в сравнение Qwen3 как одинаковый KV-cache. Условные строки и точные requests описаны в [матрице](experiment-matrix.md); конвертация/поддержка не проверялась запуском.
