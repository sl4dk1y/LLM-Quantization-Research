# Предварительный план статистического анализа

**Статус:** предварительная спецификация до просмотра любых результатов.
Подтверждающие contrasts и допуски требуют утверждения владельцем.

## Единица наблюдения и метрики

Единица качества — пара `(dataset revision, task, split, item_id)` для фиксированной конфигурации модели. Один item — одно наблюдение качества; повторный вывод того же item не увеличивает `n`. Единица performance — измеренный запрос в workload ячейке; повторы оценивают runtime variability и не считаются независимыми задачами качества.

Первичные task metrics: Accuracy для MathLogicQA, PARus, ruOpenBookQA; token-F1 для MultiQ; Exact Match для LIBRA Mini. Вторичные: MultiQ EM и ruOpenBookQA macro-F1. Внутри задачи сохраняется официальный scorer с зафиксированным source/hash. Основной когортный показатель — macro-average по task-level score, каждому task равный вес независимо от числа примеров. MERA и LIBRA агрегаты не объединяются между собой.

Порог 5 процентных пунктов — предложенный проектный margin практической значимости, а не стандарт MERA/LIBRA и не результат пилота. Неinferiority проверяется односторонней 95% границей против F16 той же модели, если она доступна. Если эталонная строка отсутствует (Qwen3-8B F16), не делать утверждение о non-inferiority.

## Объём выборки

Основная серия использует 200 примеров на каждый из трёх доступных MERA test для MathLogicQA, MultiQ и ruOpenBookQA и все 100 примеров PARus `dev`: 700 item на конфигурацию. Размер выборки закрепляется детерминированным hash-sampling до первого запуска. Тестовая выборка не используется для выбора конфигурации.

Для грубого планирования paired binary Accuracy при предположенной доле discordant pairs `q=0.25` и выявляемой разнице `δ=0.05` приближение `n ≈ 7.84 q / δ²` даёт около 784 пар. Это не пилотная оценка и не гарантирует мощность: основная серия в 700 строк на конфигурацию немного меньше; task-level выборки по 100–200 имеют меньшую мощность. Поэтому первичный вывод — macro и paired overall estimates с task-stratification, а локальные task-level эффекты — с широкими интервалами и без сильных заявлений. Если пилот показывает иную discordance/variance, sample size можно пересмотреть только до открытия test результатов и зафиксировать новой версией протокола.

LIBRA: 30 примеров в каждой ячейке task × 4K/8K/16K. Это диагностическая вторичная серия; 30 наблюдений на ячейку ограничивают точность оценки и не поддерживают тонкие выводы по малым разницам. Контролируемая performance серия: 30 повтора на length cell, три прогрева не включаются в оценку.

## Статистические процедуры

- Все сравнения качества парные, на одинаковых IDs. Для Accuracy — McNemar и paired bootstrap по item; для EM — paired bootstrap и exact binomial/пермутационный вариант, если применим; для token-F1 — paired bootstrap по item. Основной CI — 95%, стратификация по задачам/классам длины.
- Макросреднее рассчитывается сначала внутри каждой задачи, затем как простое среднее четырёх task scores. Не объединять сырые count по задачам с разной метрикой/шкалой.
- Primary contrast H1 — один заранее заданный Qwen3-4B Q4_K_M–F16 контраст; к нему не применяется поправка за множественность. Для заранее зарегистрированной семьи secondary quantization contrasts применять Holm correction; публиковать raw и adjusted p-values и 95% интервалы эффекта. При множестве exploratory сравнений подчёркивать descriptive status, не выбирать «лучшие» contrasts после просмотра.
- Размер эффекта — абсолютная разница в процентных пунктах и 95% CI; для бинарных задач дополнительно discordance counts/odds ratio при корректной оценимости. Hedges g не применять к бинарной точности.
- Performance: медиана, IQR, p95 и bootstrap CI по повторным запросам; отдельно TTFT, prefill, decode и total latency. При 30 повторах p95 остаётся нестабильной оценкой хвоста и трактуется как operational statistic, не как точная гарантия SLA.
- Публиковать долю timeout, load failure, output truncation, invalid format, memory stop и missing measurement. По основной оценке неуспешная/невалидная генерация считается ошибкой качества; отсутствие технического наблюдения помечается отдельно. Для ресурсов не заменять исключённое наблюдение нулём.

Все scorer, выборка, primary outcomes, contrasts, margins и exclusions должны быть зафиксированы до открытия held-out ответов. Никаких повторных запусков только для исправления плохого ответа; повтор возможен при подтверждённой инфраструктурной ошибке и сохраняется как новая запись с причиной.
