# Протокол измерения памяти и производительности

**Статус:** проект для утверждения и проверки в будущем пилоте; измерений на M4 Air не проводилось.
**Аппаратная цель:** MacBook Air M4, 16 GB unified memory, macOS, Metal, пассивное охлаждение.

## Различаемые величины

| Показатель | Что означает | Как использовать |
| --- | --- | --- |
| RSS | Resident set процесса в момент наблюдения | Дополнительная диагностическая серия. Не заменяет footprint и не считается общим потреблением системы. |
| Physical footprint процесса | Память, фактически приписанная процессу ОС с учётом правил Apple, включая соответствующие GPU/shared allocations | Основная процессная метрика: периодический снимок `proc_pid_rusage` (`ri_phys_footprint`) и lifetime maximum после завершения, если доступен в выбранном macOS/API. Activity Monitor Memory можно использовать как внешнюю сверку. |
| System memory used | Использование общей памяти системой и всеми процессами в момент измерения | Системная метрика для безопасности и оценки реального бюджета. Снимается через Activity Monitor / `vm_stat` и сверяется с `memory_pressure`. |
| Memory pressure | Давление на систему по доступности/перераспределению памяти | Категориальный сигнал, сохраняется из macOS `memory_pressure`/Activity Monitor. Значение не складывается с footprint и не заменяет память в байтах. |
| Swap | Использованный swap сейчас и изменение к baseline | `sysctl vm.swapusage` до/во время/после каждого запуска; считать только delta за запуск. Swap не добавляется к resident/system-used памяти. |
| Metal allocations | Backend-диагностика выделений/размещения буферов | Сохранять логи llama.cpp, число слоёв на Metal и доступный диагностический вывод. Для unified memory не прибавлять их к footprint: это может быть тот же физический пул и двойной учёт. |

Apple описывает `phys_footprint` как полезную для оценки физического расхода процесса и документирует `proc_pid_rusage`; `os_proc_available_memory` является advisory лимитом доступной процессу памяти, а не общим свободным RAM и не применяется к macOS в той же форме, что iOS. Нельзя считать RSS, footprint, память в Activity Monitor, Metal buffers и swap взаимозаменяемыми. Ссылки: [Apple WWDC: memory footprint and proc_pid_rusage](https://developer.apple.com/videos/play/wwdc2022/10106/), [`os_proc_available_memory`](https://developer.apple.com/documentation/os/os_proc_available_memory), [Apple ProcessInfo thermal state](https://developer.apple.com/documentation/foundation/processinfo/thermalstate-swift.enum).

## Частота и точки измерения

1. Снять фоновый baseline системной памяти, pressure, swap и footprint вспомогательного launcher за 60 секунд до загрузки модели; записать медиану system-used memory и текущий swap.
2. Снимать footprint целевого `llama-server`, system-used memory, pressure и swap раз в секунду от старта загрузки до завершения/выгрузки. Если возможна более частая выборка без заметной нагрузки, это фиксируется и остаётся неизменной для всей серии.
3. Зафиксировать пики по всем sampled values, lifetime max footprint, начальное/конечное значение swap, baseline и длительность интервала. Пик sampled на секунду является оценкой пика, не гарантией мгновенного максимума; это указывается в статье.
4. System-used memory сверять с Activity Monitor до и после пилотных контрольных блоков. Не складывать значения из разных окон/источников.
5. Выводы о память GPU/Metal отдельно делать только при наличии документированного и доступного для текущего macOS/API показателя с известной семантикой. В противном случае публиковать backend placement/logs как диагностику, а не как отдельную измеренную память GPU.

Основные производные:

- `M_proc_peak` — максимум `ri_phys_footprint` процесса за серию;
- `M_sys_peak` — максимум system-used memory за интервал;
- `ΔM_sys = M_sys_peak − median(M_sys baseline)`;
- `Δswap = max(swap during/after) − swap baseline`;
- `TTFT` — монотонное время от отправки запроса до первого token chunk;
- `prefill tok/s = prompt_eval_count / prompt_eval_duration` по timing-данным llama.cpp;
- `decode tok/s = eval_count / eval_duration`;
- `latency_total` — монотонное время от отправки запроса до последнего chunk/EOS.

Учитывать server start/load отдельно от TTFT и request latency. В отчёте публиковать медиану и IQR; для perf повторов — также p95 и bootstrap CI. Нулевой, отрицательный или отсутствующий denominator/timing не исправляется эвристикой, а отмечается как невалидное наблюдение.

## Условия измерений

- До начала: питание от сети; Low Power Mode выключен; одна модель; Metal offload зафиксирован и проверен по startup log; нет активной синхронизации, обновления, компиляции или другого тяжёлого процесса.
- Контрольная пауза до каждого прогона: pressure normal/green минимум 60 секунд и swap не растёт минимум 5 минут. Между моделями дождаться завершения server process и освобождения его footprint.
- Изоляция: запускать по одному запросу, без параллелизма, без нескольких загруженных моделей, фиксированные `n_batch=512`, `n_ubatch=128`, один sequence slot, KV-cache F16. Context и вывод зафиксированы в [протоколе](experimental-protocol.md).
- Temperature/thermal state запрашивается перед каждым блоком и раз в 30 секунд; дополнительно логируется событие изменения `ProcessInfo.thermalState` через доступный wrapper в будущем стенде. Состояния не трактуются как точная температура кристалла.
- Не публиковать температуру CPU/GPU, если macOS не предоставляет проверенную метрику на данном устройстве. Записывать ambient temperature, если есть независимый измеритель, с указанием его модели и положения; иначе — `not measured`.

## Предварительные ограничения безопасности

Все значения ниже — исходные проектные пороги для пилота; их нужно пересмотреть по результатам безопасного preflight, до основной серии.

| Уровень | Условие | Действие |
| --- | --- | --- |
| Допуск к запуску | Pressure normal/green 60 секунд; system-used ≤8 GiB baseline; swap delta 0 за последние 5 минут; ≥4 GiB available memory по системному индикатору | Разрешить следующий одиночный запуск. |
| Предупреждение | System-used >10.5 GiB 5 секунд; pressure yellow; swap delta ≥256 MiB; available memory <4 GiB; thermal state serious | Не отправлять новые запросы; сохранить текущий результат и диагностику; дать системе восстановиться. |
| Пауза | Serious thermal state дольше 30 секунд или pressure yellow без восстановления за 60 секунд | Остановить подачу запросов, мягко завершить текущий запрос, выгрузить модель и ждать нормализации. |
| Немедленная остановка | Pressure red/critical; system-used ≥12 GiB в течение 5 секунд; swap delta ≥1 GiB; available memory <3 GiB; thermal critical; загрузка >300 секунд; запрос >600 секунд | Перестать подавать задания; отправить SIGTERM, подождать 30 секунд; SIGKILL допускается лишь если процесс не завершился. Сохранить журнал, статус и snapshot. |

Прерывание оставляет серию возобновляемой по уникальному ключу записи. Для восстановления требуется pressure normal/green 5 минут, swap стабилен 5 минут и system-used снова ≤8 GiB. Предельная длительность одного непрерывного блока — 2 часа; после него выполнить штатную паузу и повторную проверку допуска.

## Сопоставление memory budget

Сравнения выполняются только при одинаковом workload, effective input length, контексте, batch, KV precision, фоне и источнике питания. Матched-memory пары определяются заранее: `|ΔM_sys(A) − ΔM_sys(B)| ≤ 0.5 GiB`; показывать также разницу `M_proc_peak`. Если такая пара не найдена, не расширять допуск после получения score: сообщить, что точного matched-budget сравнения нет. Дополнительно представить Pareto frontier качества против `ΔM_sys`, `M_proc_peak` и latency.

Эксплуатационный budget для правила выбора предлагается как `M_sys_peak ≤12 GiB`, при `Δswap ≤512 MiB`, нормальном pressure после завершения и без срабатывания порогов остановки. 12 GiB — консервативный заранее предложенный предел, оставляющий номинально 4 GiB из 16 GB системе; фактический резерв проверяется пилотом. Единицы GB/GiB и источник системного показателя должны быть единообразными во всём датасете.

## TTFT, prefill, decode и полная задержка

Perf sampling ведётся отдельным клиентом по monotonic clock на локальном loopback. Включить streaming. `TTFT` заканчивается при получении первого токена, а `latency_total` — при финальном chunk/EOS. Дополнительно сохранять prompt/decode token count и timing counters от сервера. При single-request режиме server очередь пренебрежимо мала, но задержка сериализации/HTTP не исключается; она одинакова для всех конфигураций и указывается.

Контролируемая perf-ячеечная серия — 30 повторов, 3 warm-up, пять конфигураций не нужны; основное предложение — Qwen3-4B F16/Q4_K_M/Q6_K × 512/4K/8K/16K. Все повторы последовательно, один model process на блок. Измерять распределение времени и токенов/с, не подменять одним средним. Подробные counts приведены в [матрице](experiment-matrix.md) и [пилотном плане](pilot-plan.md).
