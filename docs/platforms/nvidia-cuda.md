# Платформа NVIDIA CUDA и задание участнику

## Контекст

Утверждённое название исследования: «Экспериментальное исследование влияния квантования на качество и ресурсную эффективность больших языковых моделей на разнородных вычислительных платформах» (*An Experimental Study of the Impact of Quantization on the Quality and Resource Efficiency of Large Language Models Across Heterogeneous Computing Platforms*).

Цель адаптера — запуск общего quantbench и общего `llama-server` на второй конкретной системе с NVIDIA GPU/CUDA и сбор её фактических характеристик. Модель компьютера, CPU, RAM, GPU, VRAM, ОС, драйвер и версии ПО пока неизвестны. Этот документ — интерфейсное ТЗ, а не утверждение о работающей CUDA-поддержке. CUDA-адаптер должен реализовать второй участник после проверки общих контрактов владельцем.

## Сначала соберите инвентаризацию

Зафиксируйте дату, источник команды и полный вывод (секреты удалите):

| Поле | Windows | Linux |
| --- | --- | --- |
| ОС и сборка | `Get-ComputerInfo` | `uname -a`, `/etc/os-release` |
| CPU | `Get-CimInstance Win32_Processor` | `lscpu` |
| RAM | `Get-CimInstance Win32_ComputerSystem` | `free -b` |
| GPU и VRAM | `nvidia-smi -q` | `nvidia-smi -q` |
| Драйвер/CUDA driver API | `nvidia-smi` | `nvidia-smi` |
| Диск | `Get-Volume` | `df -B1` |
| Runtime | `llama-server --version` | `llama-server --version` |

Сохраните производителя/модель, байтовые значения памяти, версии, дату и ошибки команд в аппаратном manifest. Не устанавливайте CUDA Toolkit до выбора способа сборки: готовый llama.cpp может требовать только совместимый драйвер, а сборка из исходников — toolkit и компилятор.

## Архитектура и точки интеграции

Общими остаются конфигурация научного протокола, идентификация, datasets/prompts/scorer, HTTP-клиент, будущие runner/checkpoint, JSONL store и статистика. Платформенный слой содержит только capabilities, аппаратный manifest, аргументы backend и системный сбор метрик. Текущие модули: `experiments/quantbench/runtime.py`, `monitor.py`, `safety.py`, `identity.py`, `store.py`, `config.py`; общий Protocol описан в `experiments/quantbench/platform.py`. Пока команды `run`/`resume` закрыты.

Реализуйте конкретный класс, соответствующий `PlatformAdapter`: `platform_id`, `hardware_manifest()`, `capabilities()`, `runtime_args(config, model)`, `resource_snapshot(pid)`, `preflight(config)`. Не требуйте Apple-specific метрики. Для каждого поля возвращайте значение, единицу, статус `available | unavailable | not_applicable | error` и причину. Неизвестное возвращается как `null`; фиктивные нули запрещены. Недоступная обязательная для CUDA метрика блокирует preflight.

Для runtime сохраняйте loopback bind, `shell=False`, один активный процесс и один запрос. CUDA-аргументы должны проверяться и отражаться в manifest. Не меняйте общий протокол, sampling, схемы квантования, dataset IDs, результатную схему или критерии отбора.

## Метрики и безопасность

Собирайте process memory, системную RAM, VRAM процесса/устройства, GPU utilization, temperature, доступные power counters и swap/pagefile. Зафиксируйте частоту, единицы, источник и семантику. Не суммируйте RAM и VRAM; не приравнивайте их к Apple physical footprint. Power не сравнивается между системами без общей методики.

Выбор API зависит от фактической ОС и драйвера. `nvidia-smi` годится для диагностики, но проверьте стабильность полей и задержку опроса; process attribution может быть недоступна в контейнере или без разрешений. Для Windows и Linux документируйте разные источники и оставляйте отсутствующие поля явными. Мониторинг должен использовать monotonic timestamps, максимальный возраст снимка и bounded timeout.

Safety profile CUDA отдельный. Числа macOS из `config.example.json` нельзя переносить на CUDA. Критическое событие немедленно прекращает запросы и завершает только дочерний процесс quantbench; устойчивое превышение обрабатывается общим временным окном Safety Guard. Не завершайте процессы по имени и не меняйте системные настройки.

## Формат manifest и результатов

В manifest обязательны `platform_id`, ОС/версия, архитектура, CPU, RAM bytes, GPU, VRAM bytes, driver, llama.cpp version/commit, backend build flags, runtime arguments, источники/версии метрик, `protocol_hash`, hashes артефактов, `run_id`, дата и timezone. Неизвестные сведения остаются `null` до сбора.

Для результатов сохраняйте общий `observation_key` и уникальный `platform_observation_id`, включающий platform ID, `hardware_manifest_hash`, `run_id`, `attempt_id`. Пакет передачи включает исходные JSONL без изменения, manifest и SHA-256 каждого файла. Сверяйте схему, несовпадения контролируемых полей, пропуски и дубликаты до объединения.

## Тестирование и критерии готовности

1. Пройдите контрактные тесты с fake adapter без GPU-нагрузки.
2. Тестируйте ошибки, null, неприменимые и устаревшие метрики управляемыми часами.
3. Проверьте генерацию CUDA args unit-тестами; аргументы не должны менять общие настройки скрыто.
4. Проверьте loopback, тайм-ауты, остановку fake runtime и отсутствие воздействия на сторонние процессы.
5. После отдельного разрешения владельца проверьте версию llama.cpp и поддержку CUDA на своей машине; до разрешения не загружайте модели и не запускайте инференс.
6. Передайте manifest, результаты тестов, точные версии и diff на ревью. Не выполняйте Git-операции от имени владельца.

Адаптер готов к интеграции, когда manifest заполнен фактами, метрики имеют подтверждённую семантику, обязательные поля проверены, контрактные тесты проходят, CUDA args совместимы с закреплённым llama.cpp, а общие интерфейсы и формат результатов не изменены. Это не означает готовность к экспериментам: они требуют отдельного решения и окончательной фиксации протокола.

## Автономное техническое задание для разработчика

### Самостоятельное задание разработчику

Реализуйте NVIDIA/CUDA адаптер для платформенного контракта `experiments/quantbench/platform.py`. До начала реализации соберите фактическую инвентаризацию компьютера и укажите ОС, CPU, объём RAM, GPU, VRAM, драйвер, свободное место и версию `llama-server`; неизвестные параметры не заполняйте предположениями.

Реализация должна предоставлять аппаратный manifest, capabilities, безопасные backend-specific аргументы для llama.cpp и системные метрики с единицами, статусом и причиной недоступности. Сохраните ограничения loopback, запуск subprocess без shell, тайм-ауты, fail-closed для обязательных safety-метрик и остановку только собственного процесса. Не меняйте научный протокол, состав выборок и общие форматы наблюдений.

Добавьте unit- и contract-тесты на управляемых часах и fake adapter. Тесты не должны скачивать модели и датасеты, запускать реальный инференс, создавать искусственную аппаратную нагрузку или менять настройки системы. В отчёте укажите команды и результаты проверок, изменённые файлы, ограничения и метрики, которые эта ОС не предоставляет. Общие изменения интерфейса согласуются до интеграции.
