# Реализация стенда M3

**Версия реализации:** 0.2.0 (M3.2). M2 разрешён как основание для реализации стенда и будущего пилота; это не утверждает окончательный протокол основной серии. Эксперименты, загрузка моделей, датасетов и runtime-инференс не запускались.

## Состав и вызов

Код находится в `experiments/quantbench/`, тесты — в `experiments/tests/`, демонстрационная конфигурация — `experiments/config.example.json`. Зависимости runtime — только стандартная библиотека Python. Для тестирования требуется `pytest`; llama.cpp/llama-server нужен для будущей локальной оценки. M3.2 добавил runtime adapter и безопасный preflight, но `run` и `resume` остаются заблокированными до интеграции следующих частей стенда.

Из корня репозитория:

```bash
PYTHONPATH=experiments python3 -m quantbench --help
PYTHONPATH=experiments python3 -m quantbench validate --config experiments/config.example.json
PYTHONPATH=experiments python3 -m quantbench plan --config experiments/config.example.json
PYTHONPATH=experiments python3 -m pytest experiments/tests -q
```

Примерная конфигурация содержит демонстрационные нулевые хеши и локальные пути-заполнители. Перед использованием её нужно заменить реальными зафиксированными значениями. `validate` не скачивает и не открывает веса. `plan` не запускает инференс. `preflight` проверяет версию runtime, локальные файлы, свободное место и системные метрики, не загружая модель; отсутствующие метрики блокируют допуск. `run` и `resume` заблокированы. `status` и `integrity` ожидают формат полного run directory.

## Идентификация и выборка

SHA-256 канонического JSON даёт стабильный идентификатор конфигурации. Логический ключ наблюдения включает версию и хеш протокола, конфигурацию, ревизии модели и датасета, GGUF hash, квантизацию, KV-cache, split, задачу, item ID, длину контекста, workload, режим, seed и performance repeat. Идентификатор попытки отделён и включает номер повтора/запуска. Выборка ранжирует item ID по SHA-256 от `seed|revision|task|split|item_id`; пересечения split проверяются отдельной функцией.

Локальный JSONL loader проверяет точный SHA-256 файла, ожидаемый split и уникальность item ID. Это общий формат обмена, не готовый адаптер официальных MERA/LIBRA экспортов. Владелец должен утвердить поля manifest и проверить соответствие реальным схемам до пилота.

## Результаты и восстановление

`store.py` пишет JSONL append-only, синхронизируя запись на диск. Чтение обнаруживает неполный последний хвост; усечение хвоста возможно только при явном `repair_incomplete_tail=True`. Полностью повреждённые строки приводят к ошибке. Завершённые наблюдения извлекаются для будущего resume, однако runner/checkpoint orchestration пока не реализованы, поэтому автоматический resume недоступен.

## Runtime adapter

`runtime.py` формирует аргументы без shell, привязывает сервер только к loopback, сохраняет stdout/stderr в диагностический лог, проверяет `/health`, допускает один активный запрос, читает SSE `/v1/completions`, сохраняет timings и различает HTTP/network/timeout ошибки. `stop()` посылает TERM только принадлежащему экземпляру дочернему процессу, ждёт до 30 секунд и затем при необходимости использует KILL. Реальный бинарный файл не запускался; флаги командной строки и API нужно сверить с закреплённой сборкой llama.cpp.

## Источники системных метрик и ограничения

`monitor.py` использует `vm_stat` для приблизительной оценки занятых страниц, `memory_pressure -Q` для доли свободной памяти, `sysctl vm.swapusage` для объёма swap и `ps` для RSS/состояния процесса. RSS не подменяет physical footprint. Расчёт по `vm_stat` не эквивалентен Activity Monitor и требует сверки. `proc_pid_rusage/ri_phys_footprint` и `ProcessInfo.thermalState` не реализованы и возвращаются как `null` с причиной. Категориальный memory pressure также недоступен; его нельзя трактовать как нормальное состояние. `diagnose()` проверяет `llama-server --version`, не запуская сервер.

`safety.py` реализует состояния `SAFE`, `WARNING`, `BLOCKED`, `EMERGENCY_STOP`, `RECOVERY`; при отсутствии обязательной метрики инференс запрещён. Пока реализована оценка одного снимка. Временные окна порогов, блокировка до восстановления и мониторинг во время загрузки/генерации требуют отдельной интеграции, поэтому `preflight` блокирует текущую систему.

## Ограничения безопасности

Пороги M2 отражены в шаблоне: предупреждение при 10.5 GiB и 256 MiB прироста swap, остановка при 12 GiB и 1024 MiB. Это предварительные значения, не калибровка устройства. Автоматической связки Safety Guard с runtime пока нет. Текущий preflight блокирует инференс из-за недоступных обязательных thermal и physical-footprint метрик. Завершение runtime-процесса реализовано с ограниченным ожиданием; посторонние процессы не затрагиваются.

## Ещё не реализовано или не проверено

- проверка параметров и streaming API закреплённой версии llama.cpp на fake server;
- нативное получение `ri_phys_footprint`, категориального memory pressure и thermal state;
- временные окна предупреждения/остановки и мониторинг runtime во время загрузки и запросов;
- проверенные адаптеры MERA/LIBRA, официальные scorer и prompt templates;
- разбиение development/held-out по реальным манифестам и проверка пересечений на загруженных частях;
- контрольные точки, блокировка параллельного запуска, сигналы и автоматический resume;
- параметры конвертации GGUF, проверка свободного места/памяти и происхождение артефактов;
- полная целевая тестовая матрица, включая fake llama-server и системные guard.

Перед интеграционными проверками нужно получить `pytest` в `.venv` (установка в этой среде не удалась из-за DNS), добавить fake-server тесты, реализовать нативные обязательные метрики и временной safety controller, затем сверить adapter с закреплённой сборкой llama.cpp. До пилота владелец должен отдельно разрешить сам пилот. Ни одна модель или база данных настоящего исследования не использовалась при разработке тестов.
