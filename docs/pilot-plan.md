# План пилотных проверок и оценка трудоёмкости

**Статус:** план будущих проверок после утверждения M2; ничего из перечисленного не запускалось.
Пилот уточняет безопасность и длительность, но не используется как подтверждающий результат статьи.

## Последовательность пилота

Пилот не просматривает публичный test ответный набор и не переопределяет primary metric. Прежде чем основной запуск начнётся, владелец утверждает обновлённый protocol version после P0–P4 и фиксирует любые изменения.

### Объём и условная длительность пилота

P1–P4 составляют до **795 запросов**: 9 smoke (3 конфигурации × 3), 120 train-only prompt/scorer checks, 270 LIBRA checks, 360 измеряемых perf-запросов и 36 perf warm-up. P0 не запускает модели и в счёт запросов не входит. Для грубой оценки выходных токенов предлагаются caps 32 для P1, 64 для P2/P3 и 128 для P4; при полном достижении всех caps верхний предел — **75 936 новых токенов**. Это ограничение объёма, а не ожидаемая генерация.

Известная входная часть P3 составляет около 2,58 млн токенов при подстановке 4K/8K/16K как 4096/8192/16384; P4 добавляет 2,63 млн timed и 0,26 млн warm-up токенов. Итого для расчёта — около **5,47 млн входных токенов**, без prompt/scorer smoke P1–P2 и template overhead. Таблица ниже показывает только вычислительную чувствительность по известному объёму, без загрузки моделей, пауз, подготовки данных и неизвестных prompt tokens. Пропускная способность в примерах условная и не является оценкой производительности M4 Air.

| 1 000 / 10 tok/s | около 3,6 ч | Средний сценарий чувствительности, без overhead и safety-пауз. |

Стендовое wall-clock время будет больше и определяется P1/P2 prompt length, загрузкой/выгрузкой до 12 конфигурационных блоков, сбором данных, охлаждением и восстановлением. До P4 его нельзя надёжно предсказать.

## Токены и теоретическая длительность

До загрузки данных нельзя точно вычислить количество prompt tokens MERA: не скачивая corpora, известны размеры split, но не токенизированные длины по выбранным моделям. Поэтому их число будет вычислено и сохранено в P0/M3 после утверждения данных, но до запуска inference.

Для предварительной арифметики метки LIBRA 4K/8K/16K подставлены как 4096/8192/16384; реальные длины после применения task/model templates будут записаны отдельно для каждого tokenizer. Основной сценарий: 30 примеров × 3 задачи × (4096+8192+16384) = около 2,58 млн токенов на model-config; четыре context-конфигурации дают около 10,32 млн. Perf-fixture добавляет 2,63 млн timed входных токенов для 3 configs × 30 повторов × (512+4096+8192+16384) и ещё 0,26 млн warm-up токенов. Известный ввод основной серии — примерно 13,21 млн токенов, плюс MERA prompt tokens, которые нельзя вычислить без разрешённой подготовки данных; шаблоны также меняют фактическую длину.

Для минимального сценария ожидается около 2,58 млн LIBRA input tokens (10 на task×length для трёх Qwen3-4B строк), плюс 0,88 млн timed perf и 0,26 млн perf warm-up tokens. Для расширенного сценария — около 36,60 млн LIBRA tokens по доступным объёмам и тем же условным длинам в трёх задачах и четырёх context-конфигурациях, плюс 2,63 млн timed perf и 0,26 млн perf warm-up tokens. Все суммы основаны на benchmark length labels; точные model-tokenizer counts сохраняются при будущей подготовке данных. Во всех сценариях к указанным input tokens добавляются MERA prompt tokens, не вычисляемые без разрешённого локального экспорта.

Основной сценарий задаёт верхние пределы вывода: 64 токена для choice/ LIBRA, 128 для MultiQ/perf. При этих caps общий верхний бюджет около **1.11 млн новых токенов** для 14,076 запросов; фактически ответы обычно останавливаются раньше EOS, поэтому actual output tokens будут известны только после запуска. Это cap-budget, а не утверждение, что модель сгенерирует весь объём.

Теоретическое время полной основной серии после P4 оценивается по формуле:

`T ≈ Σ(I_config / R_prefill_config + O_config / R_decode_config) + N_load × t_load + N_request × t_client_overhead + T_pause`

Здесь `I` и `O` — токены входа/выхода, `R` — измеренные пилотом tok/s, `t_load` — измеренное время загрузки/выгрузки, а `T_pause` — safety-паузы и ожидание восстановления. До пилота численное wall-clock значение для M4 Air не указывается: у нас нет измеренного throughput, а фактический token budget зависит от длины ответа и prefill. Для иллюстрации чувствительности известный вход основной серии (13,21 млн, без MERA prompts) и верхний выходной cap 1,105 млн дают compute-only значения около 68,8/34,4/17,2 часа при условных парах prefill/decode 500/5, 1 000/10 и 2 000/20 tok/s. Эти значения не включают неизвестные MERA input tokens, загрузки, обработку, охлаждение, safety-паузы и ошибки; это не прогноз устройства. Ранее приведённая decode-only таблица показывает изолированный вклад максимального output cap.

## Дисковое пространство

Фактический запас до M3 неизвестен и проверяется перед подготовкой артефактов. Требование: место на один исходный высокоточный checkpoint + общий F16 GGUF + все quant GGUF, плюс не менее двух размеров самого большого из них для временной конвертации/копии и отдельное место под immutable input/outputs/логи. Для модели весы/результаты не скачиваются на M2. Публикуемый manifest включает размеры и SHA-256; raw model/data artifacts не добавляются в Git.

## План восстановления и завершения

Raw JSONL сохраняется после каждых 20 завершённых items и при остановке; состояние run marker обновляется атомарно. После перезапуска проверяются protocol/config/data hashes и compound keys, затем добавляются только отсутствующие observations. После каждой серии ожидать завершения процесса, нормализации давления, пяти минут стабильного swap и thermal state ниже serious. На следующую длинную сессию переносить только после успешного safety review.
