# Предварительный экспериментальный протокол M2

**Версия:** 0.1-draft, 24 ноября 2026 года
**Статус:** подготовлен для проверки владельцем; не утверждён. M3 не начат.
**Режим:** спецификация будущего исследования; измерений и запусков не проводилось.

## Цель и границы

Исследовать, как размер и точность весов одной локально запускаемой семьи LLM связаны с качеством ответов на русскоязычных задачах, использованием общей памяти и задержкой. Отдельная цель — проверить прозрачное правило выбора допустимой конфигурации по результатам на данных для настройки и оценить его перенос на отложенные задачи и контексты.

Основная серия использует Qwen3 Instruct в одной среде `llama.cpp`/GGUF. Весовые схемы являются фактором; точность KV-cache и прочие параметры инференса фиксируются. Qwen3.5 рассматривается отдельно как проверка переносимости на более современную архитектуру. Выводы об основной когорте не объединяются с валидационной когортой.

Протокол не предполагает разработки алгоритма квантования. Сравнивается качество и профиль ресурсов готовых конфигураций при контролируемом происхождении весов. Схемы GPTQ/AWQ и quantized KV-cache в первичный эксперимент не входят.

## Когортная структура

| Когорта | Модели | Использование |
| --- | --- | --- |
| Основная | `Qwen/Qwen3-1.7B`, `Qwen/Qwen3-4B`, `Qwen/Qwen3-8B` | Главные проверки H1–H4. Все — текстовые causal instruct-модели одного поколения; режим reasoning и шаблон должны быть одинаковыми. |
| Валидационная | `Qwen/Qwen3.5-4B` | Отдельная проверка части результатов на более новой мультимодальной модели с гибридным attention/state layout. Только текстовые входы; результаты не входят в среднее основной когорты. |

На дату среза доступен и более новый `Qwen/Qwen3.6-27B`, однако его 27B параметров и multimodal-архитектура делают его непрактичным для серии с запасом на 16 GB общей памяти. Он не включается только ради даты выпуска. Источники и ограничения указаны в [анализе моделей](model-selection.md).

Модельные ревизии M2 закреплены полными commit SHA-40 по официальным страницам истории Hub: Qwen3-1.7B `70d244cc86ccca08cf5af4e1e306ecf908b1ad5e`, Qwen3-4B `1cfa9a7208912126459214e8b04321603b3df60c`, Qwen3-8B `b968826d9c46dd6066d109eabc6255188de91218`, Qwen3.5-4B `851bf6e806efd8d0a36b00ddf55e13ccb7b8cd0a`. Перед получением артефактов в M3 следует записать SHA-256 локальных файлов и дату проверки. Для `llama.cpp` предлагается подписанный nightly-релиз `b12675`, commit prefix `c212d25`; полный commit и SHA-256 конкретного бинарного файла также фиксируются в M3.

## Факторы и оцениваемые величины

| Фактор / показатель | Уровни или определение |
| --- | --- |
| Размер и модель | Три размера основной семьи; validation-модель анализируется отдельно. |
| Схема весов | F16, Q8_0, Q6_K, Q5_K_M, Q4_K_M в пределах матрицы в [docs/experiment-matrix.md](experiment-matrix.md). |
| Тип задачи | Русское математическое решение/выбор, factual QA, multi-hop QA, причинное рассуждение и извлечение ответа из длинного контекста. |
| Длина контекста | LIBRA Mini с целевыми классами 4K, 8K, 16K; фиксированная длина фактически токенизируется отдельно для каждого tokenizer. |
| Качество | Task-native Accuracy, F1 и Exact Match; основной агрегат — невзвешенное среднее метрик по задачам после приведения каждой метрики к шкале [0,1]. |
| Ресурсы | Пиковый physical footprint процесса, максимальное системное использование памяти, memory pressure, swap delta, TTFT, prefill и decode скорость, полная задержка. |
| Контроли | Одинаковые исходные checkpoint и dataset revision, prompt и tokenizer chat template, `llama.cpp` commit/build, контекст, KV precision, batch, decoding, seed, питание, последовательность и правила прогрева. |

Для весовых сравнений каждый GGUF-производный вариант одной модели должен происходить из одного и того же официального checkpoint и общего промежуточного F16 GGUF. Путь конвертации, source revision, команды/параметры quantizer, хеш артефакта, размер файла, effective BPW и таблица типов тензоров сохраняются. Importance matrix выключена для первичного сравнения. Если пилот потребует её для совместимости или качества, это будет отдельный заранее утверждаемый фактор, а не незаметная настройка.

Качество оценивается на одном и том же наборе ID для всех сравниваемых конфигураций. Время ответа и peak memory измеряются при одном запросе за раз. Контекст, ответы, системный prompt, форматирование и stopping rules не подстраиваются под отдельные результаты.

## Источники данных и разделение выбора/проверки

Основные задачи MERA — MathLogicQA, MultiQ, PARus и ruOpenBookQA из текущего набора v1.2.0. Подбор конфигурации использует только заранее выбранные элементы `train` MathLogicQA и ruOpenBookQA (по 100 элементов в основной серии). Итоговый набор качества содержит по 200 примеров из доступных размеченных тестовых частей MathLogicQA, MultiQ и ruOpenBookQA; для PARus берётся доступный `dev` (100 примеров), так как опубликованная карточка отдельно указывает закрытый `test`. Результаты закрытого MERA-теста не входят в локальную метрику; официальный scoring можно рассмотреть позже как отдельное подтверждение, если он совместим с локально сохранёнными ответами.

Такое разделение даёт повторную проверку на отложенных примерах внутри двух задач и перенос на две задачи, не участвующие в выборе конфигурации (MultiQ и PARus). LIBRA Mini проверяет перенос на русские длинные контексты. Публичные задания могут встречаться в pretraining; разделение гарантирует невмешательство этих ответов в выбор по результатам проекта, но не доказывает отсутствие обучающего загрязнения.

LIBRA Mini: `ru_babilong_qa3`, `long_context_multiq`, `matreshka_names`; по 30 примеров на задачу и целевую длину 4K/8K/16K. Выбор фиксируется один раз, одинаковые ID используются для всех конфигураций в соответствующей когортной серии. Текущая карточка LIBRA прямо рекомендует Mini для сравнений и публикует количество объектов по task/length; источник и детали находятся в [анализе датасетов](dataset-selection.md).

Для воспроизводимой выборки сортировать доступные записи по SHA-256 от строки `seed|dataset-revision|task|split|item-id` и брать первые `n`. Предлагаемый seed — `20261124`. В манифесте сохраняются выбранные ID и хеш списка. Тестовые ID и ответы не просматриваются при настройке; скрипт/протокол выбора и конфигурация замораживаются до открытия тестовых результатов.

## Подготовка запросов и decoding

1. Для каждого примера строится ровно одно пользовательское сообщение по официальной инструкции задачи и её полям `inputs`; используется опубликованный template конкретного набора. В манифест попадает итоговый текст запроса, token count и его SHA-256. Не добавляются system prompt, few-shot демонстрации или сторонние пояснения.
2. Для Qwen3 применяется официальный chat template закреплённой модели и non-thinking режим. Для предложенного `llama.cpp b12675` режим фиксируется серверной настройкой `--reasoning off`; шаблон и передаваемые параметры сохраняются. Для Qwen3.5 применяется её собственный шаблон и тот же прямой non-thinking режим только после подтверждения поддержки на закреплённой сборке.
3. Декодирование: greedy (`temperature=0`), `top_p=1`, `top_k=0` (отключён), `min_p=0`, repetition penalty `1.0`, presence/frequency penalty `0`, seed `42`. Сохраняются имена и фактически принятые runtime-параметры; настройки, которые `llama.cpp` игнорирует при greedy-декодировании, всё равно перечисляются в манифесте как зафиксированные.
4. Лимит выдачи: 64 новых токена для MathLogicQA, PARus, ruOpenBookQA и LIBRA Mini; 128 для MultiQ. Остановка — штатный EOS/template stop. Неполный ответ из-за лимита маркируется как truncation, а не исключается.
5. Один server process, один активный запрос, без continuous batching/parallel sequences. Предлагаются `n_batch=512`, `n_ubatch=128`, один последовательный слот. При нехватке памяти эти значения не меняются между конфигурациями; сценарий сначала сокращается до более низкого контекста или останавливается.

Для обычных MERA запросов `n_ctx=4096`. Для LIBRA предельное окно задаётся как класс длины + 256 токенов резерва под template/генерацию: 4352, 8448, 16640. Никакие примеры не обрезаются. Если полный prompt вместе с зарезервированным выводом не помещается, запуск отмечается как технически неуспешный для этой ячейки; исключение и фактическая длина по model tokenizer сохраняются. Запись LIBRA с меткой длины не считается имеющей ровно столько токенов для каждого tokenizer.

## Порядок и условия запусков

- Перед каждой серией проверяется, что Mac подключён к питанию, Low Power Mode выключен, нет активного обновления/резервного копирования и не ведётся тяжёлая пользовательская работа. Версия macOS, build, состояние питания, список известных фоновых нагрузок и начальная температура/thermal state записываются.
- Конфигурации запускаются последовательно. Порядок балансируется: полный список конфигураций заранее переставляется с seed `20261124`, но контекстные прогоны сгруппированы по модели, чтобы не повторять загрузки внутри блока. Исходный порядок хранится в манифесте.
- После старта процесса выполняются три технических warm-up запроса (не входят в качество и perf выборку); затем начинается сбор. Для quality каждый item подаётся один раз. Для контролируемой performance серии — 30 повторов одной длины с заранее закреплённым текстом, три warm-up на ячейку; конкретный план дан в [плане пилота](pilot-plan.md).
- Не разрешается параллельная загрузка разных моделей. После выгрузки процесса следующая модель начинается лишь после восстановления нормального pressure и пяти минут без роста swap.
- При падении, timeout или stop сохраняются manifest, уже завершённые записи и диагностический snapshot. Серию возобновляют только по отсутствующим ключам `(protocol_id, cohort, model_revision, quant, dataset_revision, split, item_id, seed)`; существующая строка никогда не перезаписывается.

## Метрики качества

- MathLogicQA: Accuracy по выбору одной из A–D.
- PARus: Accuracy по выбору `1`/`2`.
- ruOpenBookQA: официальные Accuracy и macro-F1; Accuracy — заранее выбранная первичная метрика, macro-F1 — вторичная.
- MultiQ: официальные token-F1 и Exact Match; token-F1 — первичная метрика для этой задачи, EM — вторичная.
- LIBRA Mini: официальный Exact Match, который принимает несколько допустимых `positive_outputs` по правилам pinned evaluator.

В качестве результата задачи используется официальный scorer, закреплённый точной версией и SHA-256; его версию и извлечение финального ответа нужно проверить при preflight в M3. До проверки scorer план фиксирует строгий fallback: для выбора вычитывается первый отдельный допустимый label (`A`–`D` либо `1`–`2`); неоднозначный или отсутствующий label считается неверным. Для свободного ответа сохраняется исходный текст, а сравнение EM/F1 делегируется official evaluator; собственная normalization не подменяет его. Если официальная программа недоступна или локально не исполняется, это блокирует окончательное утверждение протокола, а не разрешает менять scorer после просмотра ответов.

Отказы, пустой ответ, невалидный формат или усечённая генерация учитываются как неуспех по primary metric; дополнительно публикуются их доли. LLM-as-judge не используется.

## Результат серии и воспроизводимость

Для каждой записи хранятся: protocol ID/version, время и порядковый номер, model/revision/full SHA-40, source и GGUF SHA-256, quant label, effective BPW и файл, llama.cpp commit/build options, macOS build, chat template, prompt text/hash и tokens, dataset revision/full SHA-40, task/split/item ID, generation parameters, completion, stop reason, score/normalization status, request time, TTFT, prompt-eval и eval time/count, process footprint, system-used memory, pressure, swap, thermal state и exception/stop reason.

Неудачные, неполные и исключённые наблюдения остаются в сыром журнале с кодом причины. Производные таблицы/графики указывают на имена и SHA-256 исходных файлов и версию расчёта. До каждого запуска фиксируется версия протокола; любые изменения создают новую версию и описываются до продолжения серии.
